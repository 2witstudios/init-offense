Orchestrator stage loop

  1. Ground. Read AGENTS.md, relevant product/architecture rules, the requested outcome and existing work. The owner's implementation instruction authorizes planning, tasking, spawning, review fixes and continuation within that outcome. A planning-only request remains planning-only.
  2. Plan and track. Keep the full objective and one durable delivery record in PageSpace. Read Issues touching the current work. Maintain build inputs separately from main acceptance obligations; Ready means useful branch progress is possible, not every prerequisite globally Done. Agents may create/claim in-scope leaves and review tasks without another permission. Preserve criteria and product intent.
  3. Coordinate. Inspect native pu status and pu logs. Coordinate actual concurrent file/resource mutations and migration generation. Package boundaries and shared concepts alone do not force serialization. Code-writing children get separate worktrees and prompts naming their parent, scope, criteria, dependencies and protected exclusions. Existing task/prompt records can be reused.
  4. Build and integrate. Actual unmerged producer commits may supply branch inputs. Pin source and integration SHAs, contracts, source owners and gaps. Separate producer approval is not required before provisional integration. Unavailable producers block dependent proof, not independent work. Proposed product authority stays provisional.
  5. Verify progressively. Run focused proof while behavior is runnable and broader gates at integration milestones. Record failed/deferred checks with candidate, reason, remaining work, responsible agent and discharge point. Continue independent work; do not churn an unchanged known blocker. Branch CI can be red. Full applicable checks must pass for main acceptance.
  6. Review and fix. Builders may spawn their own independent reviewers with native pu spawn and resolve findings without parent permission. Review stable snapshots; a mutable worktree hold lasts only while a reviewer uses it. Branch-feedback records cannot mint acceptance. No pass-count escalation; relevant delta review binds the final composed head.
  7. Accept. Require completed transitions, reconciled contracts/security, applicable gates, migration integrity and independent exact-head review under main's required checks. Autonomous agents never merge directly into main/default/protected release targets; request auto-merge only when the live main ruleset requires review-record. Done comes from independent acceptance evidence, never a builder's cherry-pick or branch push.
  8. Continue or escalate. Use pu send for meaningful milestones, final delivery, genuine blockers and actual writer conflicts. A builder can resolve routine execution issues without awaiting an explicit parent continuation. Preserve direct parent reporting and truthful delivery checks; do not duplicate delivered reports merely to collect acknowledgments. Changed product intent, scope cuts and human-only identity/secret/deployment/data actions go to the owner. Continue unaffected work and retain the original objective across context handoffs.

Receiving branch authority

Within an owner-authorized outcome, owners, point guards, root/main-level agents and worktree agents have the same non-main integration authority. Merge actual producer commits into only the receiving agent's own allocated checkout and branch. A root agent allocates an isolated receiving checkout; it never merges in the parent-main checkout. Do not modify a producer's checkout or any other agent's branch. Ordinary merge commits and conflict resolution are allowed; coordinate actual concurrent writers/resources, preserve dirty work, and never force-push, rewrite history or reset work.

Before integrating, resolve the repository's symbolic default branch (remote HEAD and live repository metadata), and inspect live target protection, including branch protection and rulesets. `main`, the default branch and protected release targets retain their existing acceptance/human protections; any other protected target also follows its protection policy. Unknown or conflicting default or protection facts do not authorize a merge. A non-main name alone is insufficient. For PR merge automation, re-read the live PR's repository, base and head, compare its base with the intended allocated receiving branch, and recheck target protection immediately before acting. Refuse a mismatch or changed candidate; never let an integration command fall through to a direct main/default merge.

Allowed unprotected non-main integration does not require global Done, separately approved producers, green whole-app CI, or root permission for each intermediate step. Pin producer and integration SHAs, contract, ownership and provisional gaps. Keep failing/deferred checks honest and preserve security and tests. Use one short-lived feature integration branch and an umbrella PR for the composed outcome; child branches need not each be main-ready. Integration grants neither Done nor main acceptance. Main/default/protected-release acceptance still needs completed transitions, applicable proof and independent exact-candidate review; production, identity, secrets, deployment and data retain human sign-off.
